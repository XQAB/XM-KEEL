# Skyward for bixi 1.0.9

机型：小米 MIX Flip 2（`bixi`，SM8750，Android 17，A/B + 动态分区；出包基线 `OS4.0.0.11.XOHCNXM`）。

1.0.8 之后的收尾版。主线是把「双系统被系统更新写掉之后」的整条链走完：旧系统留在 data 分区里的几个 GB 不再无名无姓地消失，系统页能看见、能一条条拿回；其次是本版自己的两条——发行说明不再被 `--generate-notes` 冲成一行，About 页把出包基线与当前设备并排比。

## 本次变更（1.0.8 → 1.0.9）

1. **发行说明由文件决定，不再由 GitHub 生成**（`.github/workflows/build.yml`）。`gh release create` 去掉了 `--generate-notes`，改为读仓库里的 `docs/release-notes/<tag>.md`；文件缺失时 release job 直接失败并说明原因，而不是悄悄发一条 `**Full Changelog**` 了事。v1.0.5 起四版正文都是一行的根因就是这一行命令，此后不会再出现。
2. **About 页出包基线对比**（1.0.1 五项工单的第 ⑤ 项，本版落地）。`keel-info` 现在读 recovery 自己带的那份 `prop.default`（packer 从原厂 recovery 保留下来的属性文件），按机型配置里的 `os_version_prop`（bixi 是 `ro.mi.os.version.incremental`）取出版本串，作为「出包基线」；About 页把它放在「OS 版本」下面一行，跟当前设备（recovery 从已装系统各分区 build.prop 读到的同一个属性）并排：
   - 两者相同 → `OS4.0.0.11.XOHCNXM · 与当前设备一致`；
   - 设备升过级 → `OS4.0.0.11.XOHCNXM · 当前设备 OS4.0.3.0.XOHCNXM`；
   - 已装系统读不到 → 只写基线本身，不做判断。

   原厂 recovery 的 `prop.default` 会把包名末尾的渠道码省掉（bixi 这份写的是 `OS4.0.0.11.XOHCN`，包名是 `OS4.0.0.11.XOHCNXM`），所以基线按「只差两个字母的渠道码即同一构建」的规则与 `[stock].version` 对齐，页面显示的是包名那份完整写法——这正是 `tools/verify-release.py` 里的 `same_build` 判据，CI 里两边用的是同一条规则。若镜像里那份属性文件读不出来，就退回配置里的 `[stock].version`（CI 已断言镜像里的值与它同一条构建），不会因此少一行。
3. **旧系统留下的 root 有了名字：`forgotten`**。系统更新写掉另一个槽之后，那个第二系统的 root 还在 data 分区里（用户的照片、聊天记录都在这块 root 里的镜像中），但它的 boot set 已经起不来。原先只把记录放掉，结果是几 GB 空间无名无姓地被占着：页面上没有条目、装同 id 的系统还会因为文件已存在而失败。现在它带着 `id`、名字和「被谁写掉」进 `state.forgotten`（列表，不是单条），并且：
   - 系统页在「第二系统」卡片下逐条列出：占多大、被什么写掉、为什么起不来；
   - 每条一个滑动确认，按 id 定位（不是按列表下标，读一次就可能重排），确认后删除该 root，数据一起没——所以从不自动删；
   - 装同 id 的系统前先摘掉那条 forgotten，再做空间预检（顺序反了就会得到「只剩 18 GB，不够 20 GB」而其实那 20 GB 正是要回收的那块）；
   - 空间不足的报错里直接写出「其中 N 条是被写掉的旧系统占着的 X GB」，用户知道该去哪删。
4. **系统页不再假设「这台机双系统都还在」**。`left_behind` 只在 state 里还有 forgotten 时让 worker 起来、让系统页可进——一台 boot 分区被改过、只剩 data 里那几块 root 的机器，系统页是唯一能拿回空间的地方。冷启动时 `/metadata` 并没有挂（只有设置页读过一次就拆了），所以读到 state 的那一刻用只读方式临时挂上、读完立刻还回去；fastbootd 那段记录的「进来时挂没挂」仍是 false，不会被这次读取带出多余的挂载。
5. **data 没解密时不再假装能删**。系统页把 `mounted` 提到页面级：「删除第二系统」和每条 forgotten 共用一次判断；data 没开时，两种行都改成副标题说明要先解密、点了跳到解密页，滑动确认条也不出现——不再出现滑完之后收到 `the data partition is not open` 这种英文报错。
6. **`start_as_it_stands`（原 `start_as_it_is`）**：先启动被更新的那个槽，再写 state；写不进去时 kmsg 说明「槽已切到 X，页面仍显示切换前读到的状态，再次切换会回到同一处」。两半都在有测试的模块里，用记录式的 boot control 和临时 state 文件就能验；`remove()` 也改成在 writable 闭包里重新读 state 再删它当时点名的每一个 root，不再依赖切换前抓的快照。
7. **忘记记录之外的两处小账**：`state` 里的 store 指向的 data 分区已经不在了（`/data` 被清、`/metadata` 留着）时，kmsg 与页面失败信息都直说这件事，而不是报一个找不到的 area；插件解包时掉的 x 位不再静默，kmsg 记条数与前几个文件名。

## 验证状态

- CI（tag `v1.0.9`）：Lint and test（host clippy + 全部单测）、手机端 clippy、bixi recovery 打包与 `tools/verify-release.py` 自检，全部 success；本版镜像自检 **59 项通过、0 警告、0 失败**，其中 `prop.default build: ro.build.version.incremental=OS4.0.0.11.XOHCN` 与 `[stock].version` 判为同一构建。
- 新增单测：`prop.default` 出包基线的读取（含只有 AOSP 属性名、文件不存在两种情形）；About 基线对比的三种口径（一致 / 设备已升级 / 读不到当前版本）；`forgotten` 的三条（空 state 不 offer、按 id 只删一条且保留更早那条、id 不存在时报出页面上的那句话）。
- 真机验收（主人）：本版是第一个带 About 基线对比的镜像，正文本版的第二条；真机上应看到 `OS4.0.0.11.XOHCNXM · 与当前设备一致`（当前槽 `_b`，`ro.mi.os.version.incremental=OS4.0.0.11.XOHCNXM`）。
- 双系统那条链的**真机验收本轮仍未做**：这台机 `/metadata/skyward/systems.toml` 不存在，一个第二系统都没装过，因此没有 forgotten 可看；装第二系统、模拟 OTA 写槽、刷 recovery 两槽都等主人点头。

## 已知限制（与 1.0.8 相同，未变化）

- `user 999` 打不开（recovery 里 gatekeeper 起不来），不影响 user 0。
- 两块面板不能同时驱动。
- `.7z` 容器不支持（原因见 CHANGELOG）。
- 系统「在线更新」页没有加速源。
- 双击亮屏的代价是熄屏时整机不再休眠。
- 只有「一个槽被更新写掉、既没有重新装过也没有 remove」才会留下 forgotten 的 root；重新装同一个 id 或整份移除都会把它带走。

## 校验方式

只认 sha256：对照 `SHA256SUMS`，或直接

```
sha256sum skyward-v1.0.9-bixi-OS4.0.0.11.XOHCNXM.img
```

## 刷入

```
fastboot flash recovery skyward-v1.0.9-bixi-OS4.0.0.11.XOHCNXM.img
```

这台机器用 `fastboot flash recovery` 刷 100MB 的镜像会在中途断链（`Write to device failed (no link)`），更可靠的是在本机 root shell 里 `dd if=…img of=/dev/block/by-name/recovery_a bs=1048576`；也可以直接在 recovery 的「设置 → Skyward 更新」里取同一份 `.img`。
